# OAMS Platform — System Architecture & Full Structure

> Proprietary internal blueprint for turning the OAMS site into a full SaaS
> e-commerce + marketplace platform. **Read the whole doc before touching code.**

---

## 1. What we're building

A single platform replacing the current static store with three interlocking
surfaces:

| Area | Who | What it does |
|------|-----|--------------|
| **Shop** | Everyone | Existing storefront (products, cart, checkout) now backed by a real database |
| **Marketplace** | Registered **Sellers** | Post products for sale, manage listings, see real-time **clicks / views / sales** per product (like a Facebook feed of listings) |
| **Admin** | **Admins** | Add / edit / remove products, manage + process orders, manage users & sellers, view platform analytics |

A **generic SaaS analytics engine** powers every "how many people clicked this"
number in the system. Images are optimised server-side and stored in small,
fast-to-serve formats.

## 4. Database Schema (Prisma → PostgreSQL)

Ecosystem in DB terms:

- **User** — everyone. `role: USER | SELLER | ADMIN`. Sellers get store/profile fields.
- **Product** — one table powers *both* the store catalog (official, `sellerId = null`)
  and marketplace listings (`sellerId` set, `marketplaceEnabled = true`).
- **ProductImage** — many images; stores the small optimized variants.
- **Order / OrderItem** — checkout with status lifecycle. `OrderItem.sellerId`
  lets each seller see the payouts for their own items.
- **AnalyticsEvent** — the SaaS engine. Append-only event rows.
- **Session** — optional token revocation (session blacklist/invalidation).

Order status lifecycle:
`PENDING → PAID → PROCESSING → SHIPPED → DELIVERED` (+ `CANCELLED | REFUNDED`).

`AnalyticsEvent.type` enum (the "full SaaS click system"):
`PAGE_VIEW, PRODUCT_VIEW, PRODUCT_CLICK, LISTING_VIEW, LISTING_CLICK,
EXPAND, ADD_TO_CART, CHECKOUT, PURCHASE, SEARCH`.

The full Prisma schema lives in [`prisma/schema.prisma`](../prisma/schema.prisma).

## 5. API Surface (Route Handlers)

| Method | Path | Purpose | Auth |
|--------|------|---------|------|
| POST | `/api/auth/register` | create account (USER) | public |
| POST | `/api/auth/login` | set httpOnly JWT cookie | public |
| POST | `/api/auth/logout` | clear cookie | any |
| GET | `/api/auth/me` | current user + role | any |
| GET | `/api/products` | public catalog (query: category, page, seller) | public |
| GET | `/api/products/[id]` | one product (also records a view event) | public |
| POST | `/api/admin/products` | create official product | ADMIN |
| PATCH/DELETE | `/api/admin/products/[id]` | update / remove | ADMIN |
| POST | `/api/marketplace/products` | seller lists a product | SELLER |
| PATCH/DELETE | `/api/marketplace/products/[id]` | manage own listing | owner SELLER |
| GET | `/api/marketplace/stats` | my clicks/views/sales aggregates | SELLER |
| POST | `/api/orders` | place order (from cart) | USER |
| GET/PATCH | `/api/admin/orders` · `/api/admin/orders/[id]` | list / process orders | ADMIN |
| POST | `/api/uploads` | image upload (multi) → sharp → variants | SELLER/ADMIN |
| POST | `/api/events` | client analytics ingest | public (rate-limited) |

Policies: all routes validate with **zod**; DB writes go through Prisma;
sensitive routes check role via the JWT session helper.

## 6. Analytics Engine (the "full SaaS click system")

Design: **event sourcing + rollups**, so it scales and stays accurate.

1. **Ingest** — the UI (or the server on view render) sends small
   `POST /api/events` with `{ type, productId?, listingId?, sessionId, ref }`.
   The route records an `AnalyticsEvent` row (device/UAm parsed server-side).
   Fire-and-forget from the client, rate-limited.
2. **Store** — append-only table. Row inserts are cheap; writes are batched.
3. **Aggregate** — reporting uses SQL `GROUP BY` over the table plus optional
   daily **materialized rollups** (`rollup_daily_events`) maintained by a cron
   for fast dashboards on big datasets.
4. **Expose** — one `analytics.summarize(userId)` helper returns per-product
   `{ clicks, views, addToCarts, sales }` for the seller dashboard; admins get
   platform totals.

Every "how many people clicked" number in the marketplace dashboard is served
by this engine — no page-local counters.

## 7. Image Pipeline ("store imgs in small form for fast rendering")

`src/lib/images.ts` runs **sharp** on every upload:

```
upload (original jpg/png)
  → decode, limit longest side to 2048px (master)
  → generate variants:
       large   1280px  WebP q≈80
       medium   800px  WebP q≈70
       thumb    480px  WebP q≈70   (cards/feed)
       tiny     240px  WebP q≈60   (avatar/icon)
  → save to public/uploads/{productId}/{id}_{size}.webp
  → persist variant URLs in ProductImage
```

Result: images are ~60–75% smaller than the source, in a modern format, with
`sizes`/`srcSet` served to browsers so **cards load only the tiny/thumb
renditions** and zoom uses large. nginx emits long `Cache-Control` for
immutability. Optional Cloudinary mode is preserved as a CDN fallback
(see `.env.example`).

## 8. Auth & Roles

- Passwords hashed with `bcryptjs`.
- On login: sign a **JWT** (`jose`, HS256) with role + user id, store in an
  **httpOnly, Secure, SameSite=Lax** cookie.
- Helpers: `getSession()`, `requireRole('ADMIN' | 'SELLER')` used in Route
  Handlers and server components.
- **Admin bootstrap:** first run seeds an admin from `ADMIN_EMAIL`/`ADMIN_PASSWORD`.
- Sellers request/stay sellers via role upgrade (admin approves) — optional gate.

---

## 9. Order Flow

1. Cart is client local + synced to server when checking out.
2. `POST /api/orders` validates stock, creates `Order` + `OrderItem`s, records
   `PURCHASE` events, decrements stock, emails confirmation via nodemailer/SMTP.
3. Admin sees `PENDING` orders → `PAID` → `PROCESSING` → `SHIPPED` → `DELIVERED`.
   Each transition is timestamped and audited.
4. Sellers see only their own order items + running payout totals.

## 10. VPS Deployment (Docker)

- `docker-compose.yml` runs **postgres:16** (persistent volume) + the **app**.
- `Dockerfile` = multi-stage: build Next.js → `next start` (Node server).
- `nginx/` reverse-proxies on 80/443, TLS via certbot, proxies `/` to the app
  container; volumes: uploads + letsencrypt.
- `prisma migrate deploy` runs on container start; `seed` on first boot.
- **GitHub Pages is retired**; the repo now deploys to a VPS.

## 11. Phased Rollout

- **Phase 1 ✅ (this commit):** blueprint doc + foundation (schema, lib, env,
  docker, deps, types).
- **Phase 2 ✅:** REST API (auth, products, orders, events) + `/api` route handlers.
  Auth: `register | login | logout | me`. Admin: products CRUD + orders status.
- **Phase 3 ✅:** Admin panel UI — `/admin/login`, dashboard, products CRUD,
  orders processing.
- **Phase 4 ⏳:** Marketplace (seller dashboard, listing CRUD, stats UI).
- **Phase 5 ⏳:** image pipeline + upload UI, email, payments, harden (rate limits).
